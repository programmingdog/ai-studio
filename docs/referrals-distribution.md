# 邀请注册、两级分润与人工提现

## 已确认的业务规则

- 邀请归因采用“公开邀请页注册并绑定 → 下载客户端 → 使用同一账户登录”。不依赖跨浏览器 Cookie、设备指纹或安装包携带用户信息；直接下载安装后另行注册不会自动归因。
- 分润基数是购买积分套餐的**人民币实付金额**。不按赠送积分、积分消耗数量、套餐标价或人工调整积分计提。
- 最多向直接上级、上上级两人分润，不向第三级继续递归。
- 邀请积分与人民币分润是两个独立账本，积分不能通过此功能兑换为提现余额。

## 初始化与配置

在项目根目录执行：

```powershell
npm run db:migrate
npm run db:backfill-invites --workspace @aivs/server
npm run build:all
```

新增迁移为 `021_referrals_distribution.sql`、`022_payout_operator_claim.sql` 和 `023_user_commission_balance.sql`。已执行的迁移不可再修改；后续调整应增加新迁移。升级部署时先迁移，再部署并重启服务端，更新后台与客户端。邀请码回填脚本可重复运行，仅给尚无邀请码的既有用户生成代码，不绑定上级、不补发奖励、不回算旧订单；023 迁移从既有分润钱包回填用户余额。

后台“设定 → 分销配置”包含：

| 配置 | 初始值 / 用途 |
| --- | --- |
| 分销开关 | 关闭；不开启不会产生新的人民币分润 |
| 直接、间接比例 | 均为 0%；启用前填写，两者合计大于 0% 且不超过 100% |
| 最低提现金额 | 100 元，可修改 |
| 邀请奖励积分 | 每位新注册用户 20 积分；设为 0 暂停新奖励 |
| 邀请页基础地址 | 默认后台来源域名加 `/invite`；生产需填写实际公开 HTTPS 地址 |
| Windows / macOS 下载地址 | 初始为空，需填写已发布安装包的 HTTPS 地址 |

公开邀请页由管理网站提供，路径 `/invite/{invite_code}`，不要求管理员登录。示例基础地址为 `https://你的域名/invite`，不要填到 API 地址或包含某位用户的邀请码。生产环境须设置管理网站的 `NEXT_PUBLIC_API_BASE_URL`，并把公开网站来源加入服务端 `ADMIN_ORIGIN` 或 `CLIENT_ORIGINS`；不要在浏览器生产构建中保留 localhost API。

分享链接不包含邮箱等资料。落地页沿用邮箱图形验证与邮件验证码接口：先弹出自定义图形验证窗口，再发送邮件；注册成功后绑定邀请关系并提供下载按钮。网页不持久保存登录令牌，注册产生的临时网页会话会退出；客户端使用该邮箱和密码正常登录。

## 邀请关系与奖励

- 每个账户有 `pid` 和唯一八位 `invite_code`。代码由安全随机数生成，保证包含字母、数字，数据库唯一索引处理碰撞；既有用户可通过回填脚本或读取资料补齐。
- 普通新用户 `pid=NULL`；从邀请页注册时，服务端由邀请码查找有效邀请人，不能直接提交任意 `pid`。
- 绑定仅发生在新账户的注册事务中，不提供重新绑定、改上级、自邀接口。被停用邀请人不能接收新绑定。
- 账户建立、积分账户建立、邀请关系和奖励积分账本同时提交或同时回滚。每个被邀请账户有唯一奖励记录，重复请求不重复发放。
- 微信公众号带参二维码会话 API 支持可选 `invite_code`，服务器保存会话对应的邀请人；未关注用户的关注事件和已关注用户的扫码事件走同一绑定流程。只在新微信账户创建时绑定，已有微信账户不重新绑定。当前公开邀请页采用邮箱注册下载流程。

## 分润入账

用户表已包含 `pid`、`invite_code`，迁移 `023_user_commission_balance.sql` 新增 `balance_fen BIGINT UNSIGNED NOT NULL DEFAULT 0`（人民币分）。这是当前尚未打款的分润总余额，而非历史累计收入：`balance_fen = available_fen + frozen_fen = earned_fen - paid_fen`。提现申请仅冻结、不再次扣总余额；实际打款后扣总余额，驳回只释放冻结。每次钱包和流水变更均在同一事务中同步用户余额，不能通过用户资料编辑接口改余额。迁移从既有钱包回填，避免清零历史余额。

后台用户列表展示分润余额、可提现金额、冻结金额、上级基本资料、直接及间接下级人数。“查看上下级”可查询上级资料，以及分别分页的一级/二级下级列表；每页50人，并可进入某个上级/下级继续查看关系。人数依据 `users.pid` 统计，包含停用账户，不计第三级；与是否曾发放邀请积分无关。关系查询接口为 `GET /admin/users/{userId}/relations?level=1&page=1`，沿用 `users.read` 权限。

当前真实付款入口是微信 Native 积分套餐支付。回调通过 RSA 签名校验与 AES-GCM 解密，核对商户、AppID、订单金额和币种后，使用 `amount.payer_total` 计提，要求 `payer_currency=CNY`。微信将该字段定义为用户实际支付金额，单位为分，扣除优惠部分：[微信支付官方支付通知文档](https://pay.wechatpay.cn/doc/v3/merchant/4012791861)。

公式：`分润金额（分） = floor(实付金额（分） × 比例基点 / 10000)`。使用整数运算，不采用浮点四舍五入；1000 基点等于 10%。例如 C 实付 10 元、直接比例 10%、间接比例 5%，B 收入 1 元、A 收入 0.50 元，A 的上级没有收益。

积分到账、支付订单更新、分润结算快照、分润钱包及流水在同一事务完成。订单、通知及分润记录的唯一约束防止重复入账。结算快照保留当时的开关、比例、实付金额和配置版本；后续修改配置不会改写历史。关闭期间或实付为零的订单也留结算标记，之后开启不补算。

被停用的收益用户不计新分润；不会把失效一级的比例转给其他级，也不会补位到第三级。人工添加积分购买记录、改积分或消耗积分不会触发分润。

## 提现与打款

用户入口在“账户中心 → 分润与提现”。每周五北京时间 00:00（含）至周六 00:00（不含）开放申请，以服务端时钟为准。金额须达到最低金额且不超过可提现余额。关闭分销后，既有收益仍能依照周五与最低金额规则申请。

必须提交支付宝实名、账号及不超过 256KB 的 PNG/JPEG 收款码。图片只接受内嵌 data URL，拒绝 SVG 和外部链接。三项收款资料组成不可变快照，使用服务端 `CREDENTIAL_ENCRYPTION_KEY` 对应的 AES-256-GCM 加密存储。此密钥必须备份；直接更换而不迁移密文会导致旧收款资料无法解密。使用 HTTPS，避免在代理/业务日志中记录完整请求体。

| 状态 | 资金处理 | 后台操作 |
| --- | --- | --- |
| PENDING 待审核 | 可用余额转冻结 | 通过，或填写原因驳回 |
| APPROVED 待打款 | 保持冻结 | 领取打款任务，或驳回 |
| PROCESSING 已领取 | 保持冻结 | 仅领取人完成打款记账；未实际打款可确认后释放任务 |
| REJECTED 已驳回 | 冻结退回可用，仅一次 | 只读 |
| PAID 已打款 | 冻结扣除，计入累计已打款，仅一次 | 只读 |

管理员流程：

1. 在“提现申请”审核申请；通过不会发起转账。
2. 打款管理员点击“领取打款任务”，此时只有该管理员能确认打款；其他管理员不能再领取。
3. 核对解密的收款资料，在支付宝中手动完成转账。
4. 输入支付宝交易流水号、说明，明确勾选“已完成实际打款”，再登记。流水号全局唯一；同申请同流水重试不会重复扣除冻结余额。
5. 在“打款记录”核对已登记记录。

关闭弹窗或断网不会释放任务。若确认结果不明，先核对支付宝流水和后台记录，不要再次转账。如果确实未打款，领取人须明确勾选“尚未实际打款”并填写原因才能释放，之后可以重新领取或审核驳回。没有自动超时释放，避免已实际支付但尚未记账的任务被他人再次支付。

用户提交提现有独立幂等键：未修改资料直接重试复用原键，服务端返回同一申请，不重复冻结。同一键换金额/资料会被拒绝。关闭软件重启后遇到不确定结果，先查申请记录再决定是否新申请。

后台新增“邀请奖励、分润记录、提现申请、打款记录”，支持分页和用户筛选；提现额外支持状态筛选。用户只能查询自己的记录。账本和打款记录没有直接编辑、删除接口。

## 权限、运维与边界

- `configs.manage`：读分销配置；保存还需 `distribution.manage`。
- `distribution.manage`：读管理记录、审核；`payouts.manage`：解密收款资料、领取/释放任务、登记打款。负责打款的管理员应同时具备记录查询权限。超级管理员已自动获得新增权限。
- 所有配置保存、审核、敏感资料查看、领取/释放、打款登记写入审计日志。普通列表不返回收款资料或密文。
- 每个用户满足：`累计分润 = 可用 + 冻结 + 已打款`；可用/冻结分别应与 `commission_wallet_entries` 的增量合计一致。定期与支付宝手工流水对账。
- 本功能不会自动调用支付宝转账接口，也不能判定管理员声称的转账是否真实到账；必须执行人工核账。
- 当前项目没有启用退款回调与自动退款流程。本次不新增退款业务；如后续增加套餐退款、拒付，必须同时设计分润冲正、已提现追偿及人工复核，不要仅修改原支付记录。线上运营前应核实退款政策和处理流程。
- 仅限制两级并不保证运营模式自动合规；启用前应就推广方式、奖励机制、税务及支付资料处理完成合规审核。

## 验证

常规无网络单元测试：

```powershell
npm run build --workspace @aivs/server
node --test apps/server/test/*.test.cjs apps/admin-web/test/*.test.cjs apps/desktop/test/*.test.cjs
```

可选真实 MySQL 集成测试（使用服务端 `.env`，先执行迁移）：

```powershell
$env:AIVS_TEST_DB='1'
node --test apps/server/test/referrals-db.test.cjs
Remove-Item Env:AIVS_TEST_DB
```

该测试使用合成账户及本地生成的 RSA/AES 测试凭据，不发邮件、不创建外部订单、不实际转账。所有数据库修改被包在一个最终必定回滚的事务中；服务事务用 savepoint 隔离，会短暂锁配置行，建议在测试环境或低流量时运行。重叠请求测试使用序列化事务适配器，不替代生产多连接压力测试。

界面隔离测试服务器：`npx vite --config tests/referrals-preview/vite.config.ts`，访问 `http://127.0.0.1:1432/admin.html`、`desktop.html`、`invite.html`。这些测试专用入口将应用 API 模块替换为不含 `fetch` 的本地模拟，不能创建真实申请、发送邮件或修改配置；不属于生产构建入口。
